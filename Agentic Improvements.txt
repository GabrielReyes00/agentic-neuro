1. SYSTEM OVERVIEW
================================================================================

This repo is the backend for an AI-powered neurosurgery learning system.
It runs as a local CLI agent (Claude Code or Gemini CLI) that:
  - Retrieves information from 22 neurosurgery textbooks via vector search
  - Tracks the user's mastery of 265 ACGME curriculum topics via a knowledge graph
  - Writes structured study material to an Obsidian vault for visual review
  - Syncs Anki flashcards via the AnkiConnect API
  - Provides Socratic tutoring sessions, clinical simulations, and operative walkthroughs
  - Generates research reports with RAG-sourced citations
  - Manages inbox triage and calendar scheduling via MCP

Multi-agent: Claude Code (CLAUDE.md) and Gemini CLI (GEMINI.md) share the
same Python backend, databases, and Obsidian vault. Agent-specific behavior
is configured in their respective system instructions; all Python scripts are
agent-agnostic.

1b. KEY TECHNOLOGY CHOICES

  Vector DB:      LanceDB (local, columnar, fast)
  Embeddings:     BAAI/bge-m3 (1024-dim, multilingual, MPS-accelerated)
  Reranker:       cross-encoder/ms-marco-MiniLM-L-6-v2 (sigmoid scoring)
  NER:            SciSpacy en_ner_bc5cdr_md (medical entity extraction, optional)
  Knowledge DB:   SQLite via custom ORM in knowledge_graph.py
  Decay Model:    Stability-weighted Ebbinghaus: half_life = 48h * 2^(depth-1) * stability_factor
  Vault:          Obsidian with Dataview plugin (inline field queries)
  Anki:           AnkiConnect localhost:8765
  MCP:            Gmail, Google Calendar
  Agent:          Claude Code (Opus 4.6 primary) + Gemini CLI (Flash/Pro)

6. KNOWN LIMITATIONS AND TECH DEBT
================================================================================

  6a. THE ACTIVE RECALL DEFICIT (CRITICAL — systemic)
      Of 480 signals: 201 card_created, 191 query, 84 study_session, 1 correct_recall.
      The system overwhelmingly creates cards and retrieves text. It almost never
      tests the user and records the outcome. The stability model rewards active
      recall 5-10x more than passive exposure, but there is almost no active recall
      data flowing in. This means:
        - Confidence values are dominated by decay, not by demonstrated mastery
        - Stability factors cluster narrowly (2.35-7.95) instead of spanning the
          full 1.0-10.0 range
        - The difficulty column is at default 0.5 for 236/238 topics
      ROOT CAUSE: Skills (study-session, intern-bootcamp, rag-workflow) use
      log_study and log_event with signal_type="study_session" or "query" for
      most interactions. Even when the user answers a question correctly in a
      Socratic session, the skill logs it as "study_session" rather than
      "correct_recall" or "incorrect_recall". The signal taxonomy exists but
      skills don't use it granularly.

  6b. SESSION STRATEGIES RECORDED BUT NEVER CONSUMED (HIGH)
      session_narratives.next_session_strategy contains actionable text like
      "reinforce the distinction between ALIC and PLIC" and "start by
      reinforcing medial-to-lateral orientation in the lateral ventricle floor."
      No skill reads this when starting a new session. Each session starts
      stateless. The system has memory but no recall.

  6c. ZERO PREREQUISITE EDGES (MODERATE)
      All 15 concept_relationships are confusable_with. Zero prerequisite_of,
      extends, or differentiates_from edges exist. seed_prerequisites returns
      0 edges (the co-occurrence seeder needs more data). Canvases show
      unconnected colored grids instead of learning paths.

  6d. CALIBRATION SYSTEM INERT (MODERATE)
      calibration_profile returns all nulls. No calibration_log entries.
      teaching_failures and key_confusions_json are empty arrays in all 6
      session narratives. The system cannot detect overconfidence — critical
      in medical education.

  6e. ANKI PIPELINE UNTESTED (MODERATE)
      anki_card_stats has 0 rows. The card creation signals (201) show cards
      were drafted but never dispatched to AnkiConnect. The full pipeline
      (dedup -> validate -> dispatch -> stat tracking) is unverified.

  6f. NO AUTOMATED TESTS (LOW-MODERATE)
      Zero pytest coverage. All validation is manual or via post-session hook.
      Each iteration's migration scripts are tested manually then left as
      one-shot tools. Regressions are caught by users, not CI.

  6g. LANCEDB API DEPRECATION (LOW)
      table_names() deprecated; should use list_tables().

  6h. SINGLE-TEXTBOOK SEARCH (LOW)
      lance_retriever.py searches all 22 textbooks. No per-book filter.

7. FUTURE DIRECTIONS (prioritized by impact on learning experience)
================================================================================

  --- THESIS ---

  The infrastructure is stable. The database is clean. The SRS model works.
  The vault renders correctly. The next phase is not about building more
  infrastructure — it is about making the system INTELLIGENT: using what it
  knows to change what it does, and generating the high-quality signal data
  that makes the entire KG meaningful. Every item below is evaluated against
  one question: does this make the next study session measurably better?

  ============================================================
  TIER A — TRANSFORM THE LEARNING EXPERIENCE
  ============================================================
  These items directly change what happens when the user sits down to study.

  A1. GRANULAR SIGNAL LOGGING IN SKILLS (CRITICAL — unblocks everything)
  -----------------------------------------------------------------------
  WHY: This is the single highest-leverage change. The stability model, SRS,
  difficulty tracking, calibration, and smart recommendations ALL depend on
  correct_recall / incorrect_recall / partial_recall signals flowing in. Right
  now, 82% of signals are passive. Until skills log granular outcomes, every
  downstream intelligence feature operates on noise.

  WHAT:
    (a) Audit all learning skills (study-session, intern-bootcamp, rag-workflow,
        study-material) for every point where the user answers a question.
    (b) After each user response in a Socratic/drill exchange, the skill must
        call log_event with the appropriate signal_type:
          - correct_recall: user answered correctly without hints
          - partial_recall: user got the right direction but missed key details
          - incorrect_recall: user answered incorrectly or gave a misconception
          - drill: user completed a structured drill item correctly
    (c) Each log_event call must include the specific concept being tested
        (not the broad session topic), the depth level, and the domain.
    (d) Update skill command files (.claude/commands/ and .gemini/commands/)
        with explicit logging instructions and examples.

  SCOPE: Modifications to 4-6 skill command files. No Python changes needed —
  log_event already supports all signal types. ~20-30 lines per skill.

  VALIDATES:
    - Run a 10-question study session. Verify >= 8 signals logged as
      correct_recall/incorrect_recall/partial_recall (not study_session).
    - After session: difficulty column updated for tested topics (not 0.5).
    - Stability factors for tested topics diverge based on signal quality.

  ENABLES: A2, A3, A4, B1, B2 — essentially everything downstream.

  A2. SESSION CONTINUITY ENGINE (HIGH — the "tutor that remembers" feature)
  -------------------------------------------------------------------------
  WHY: The system records next_session_strategy but never reads it back.
  Each session starts cold. This is the difference between a stateless
  Q&A tool and a tutor that knows your history. "Pick up where you left
  off" is transformative for spaced learning.

  WHAT:
    (a) New KG command: session_context --skill <skill> [--topic <topic>]
        Returns the most recent session narrative for that skill/topic,
        including: next_session_strategy, key_confusions, teaching_failures,
        topics studied, coverage gaps, last depth level.
    (b) Skills query session_context at startup and inject the result into
        their opening prompt. E.g., "Last session (Apr 11): covered
        hypertension management. Strategy: begin with interactive drilling,
        starting with recall and spatial concepts. Key gaps: [list]."
    (c) If topic matches a previous session, the skill opens with a targeted
        warm-up on previously missed concepts before advancing.
    (d) Heartbeat now records mid-session checkpoints that session_context
        can surface (e.g., "you were at Q15/38 last time").

  SCOPE: ~80 lines in knowledge_graph.py (new CLI command, queries
  session_narratives + signal_events). ~20 lines per skill command file.

  VALIDATES:
    - Start study-session on a previously studied topic. Verify the opening
      prompt references the prior session's strategy and gaps.
    - Start intern-bootcamp. Verify it surfaces the most recent narrative.

  A3. PREREQUISITE EDGE SEEDING FROM CURRICULUM STRUCTURE (HIGH)
  ---------------------------------------------------------------
  WHY: With 371 curriculum-linked topics, clean PGY/priority/domain data,
  and 265 curriculum entries with structured metadata, rule-based prerequisite
  inference is feasible. This transforms canvases from colored grids into
  directed learning paths. It also enables blocking_gaps and concept_chain
  to return meaningful results (currently they return nothing useful with
  0 prerequisite edges).

  WHAT:
    (a) Within-domain PGY ordering: PGY-1 topics prerequisite_of PGY-2+
        topics in the same domain.
    (b) Priority band ordering: core (priority 1) topics prerequisite_of
        advanced (priority 3) topics in the same domain.
    (c) Cross-domain anatomy prerequisites: MK-Neuroanatomy topics are
        prerequisites for surgical topics that reference the same anatomy
        (token-overlap matching on anatomical terms).
    (d) Conflict guard: never create prerequisite between confusable_with
        pairs (those are peers, not prerequisites).
    (e) Use seed_prerequisites command (already exists but returns 0 edges
        due to co-occurrence threshold) OR write a new curriculum-based seeder.

  SCOPE: ~150-line script or modification to seed_prerequisites in
  knowledge_graph.py. Uses curriculum_skeleton.json + topics table.

  VALIDATES:
    - 50-100 prerequisite edges created.
    - Canvas edge count jumps from ~10 to 60+.
    - Manual spot-check of 15 edges for medical correctness.
    - blocking_gaps --topic "X" returns meaningful prerequisite chains.

  A4. INTELLIGENT STUDY PLANNER (HIGH — the "what should I study" upgrade)
  -------------------------------------------------------------------------
  WHY: "What should I study?" currently returns a flat list of never-seen
  curriculum topics sorted by priority. It ignores cognitive patterns
  (11 identified), session strategies (6 recorded), confusable pairs
  (16 in matrix), error type concentrations, and prerequisite chains.
  A study planner that synthesizes all signals would be the most valuable
  daily-use feature for board prep.

  WHAT:
    (a) New KG command: study_plan --hours N [--rotation <rotation>] [--focus <domain>]
    (b) Output is a prioritized sequence with rationale for each item:
        Layer 1: Overdue high-confidence topics (SRS spaced repetition)
        Layer 2: Confusable pairs with recent errors (error correction)
        Layer 3: Prerequisite chains for upcoming curriculum (preparation)
        Layer 4: New curriculum topics by PGY priority (expansion)
    (c) Each item includes: topic, recommended skill, estimated time,
        rationale ("3 errors on this pair in last 2 sessions", "prerequisite
        for tomorrow's rotation topic").
    (d) Integrate into study-session skill as the default session plan.

  SCOPE: ~200 lines in knowledge_graph.py. ~30 lines in study-session skill.
  BLOCKED BY: A1 (needs signal data), A2 (session context), A3 (prerequisites).
  Can be partially useful without A3 but reaches full potential with all three.

  VALIDATES:
    - study_plan --hours 2 returns a multi-layer plan with rationale.
    - Plan prioritizes overdue items over never-seen items.
    - Plan includes confusable pair drills when error history exists.
